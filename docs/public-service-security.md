# 회원 서비스와 광고 도입을 위한 보안 설계

개인용 모아와 회원용 비공개 테스트는 서로 다른 Sites 프로젝트와 데이터베이스를 사용한다. 회원용은 기존 장부를 가져오지 않고 새 데이터베이스에서 시작한다. 공개 범위를 변경하기 전에 아래의 현재 보호 장치와 검증 사항을 확인한다.

## 회원용 테스트에서 사용할 기능

- 백업 및 데이터 관리에서 내역을 열람·내보내기·수정하고 삭제할 수 있다. 삭제 시 현재 로그인한 계정의 장부와 보기 설정을 빈 값으로 바꾸고 상담 사용기록을 삭제한다. 이전 화면에서 삭제된 자산을 다시 저장하지 못하도록 계정 ID와 빈 기록의 버전은 남긴다. ChatGPT 계정과 호스팅 백업 삭제는 별도 절차다.
- AI 상담 버튼을 누르면 해당 상담에 필요한 정보와 OpenAI 전송 및 보관 가능성을 안내한다. 확인한 요청만 서버에서 처리한다. 상환 비교는 각 시나리오의 계산 결과를 설명하며, 화면에서 고른 상환 전략은 이용자가 변경한다. 회원용 테스트에서는 API 키를 연결하기 전까지 상담이 비활성화된다.
- 회원용 빌드는 자체 아이콘과 이름 첫 글자를 사용한다. 공개용 약관을 대신하지 않는 비공개 테스트 데이터 안내를 로그인 화면과 설정에서 확인할 수 있다.

## 공개 전 운영자 확인 사항

- 처리방침에 넣을 운영자 이름과 개인정보 문의처, 처리별 법적 근거, 위탁 계약 및 업체·처리 국가·보유기간을 확정한다.
- 실계정 2개로 로그인 세션과 장부·보기 설정·내보내기 격리를 확인하고 운영 데이터 백업 만료 및 복원 절차에서 삭제한 내역의 재노출을 막는 방법을 검증한다.
- 사용자가 보내는 실제 금융정보는 오류 집계, 광고, 예시 데이터, Git 기록에 넣지 않는다. 공개 이력에 남은 테스트 항목명은 저장소 운영 설정까지 포함해 정리 범위를 판단한다.

## 현재 확인한 보호 장치

- 호스팅 접근 권한은 소유자 1명으로 제한되어 있다.
- 저장 API는 호스팅 인증에서 받은 계정 ID로 데이터를 조회·수정한다. 사용자 입력으로 저장 대상 계정을 고르지 않는다.
- 비로그인 요청 차단, 쓰기 요청 출처 검사, 서버 입력 검증, 저장 버전 충돌 검사, API 응답 캐시 금지가 있다.
- 금융기관 로그인 정보·전체 계좌번호·주민등록번호를 요구하지 않는다. GitHub에는 코드만 저장한다.
- 외부 스크립트를 허용하지 않는 CSP를 사용한다. 현재 광고 코드를 실행하지 않는다.
- AI 상환 상담은 운영자가 Sites 비밀 환경변수로 연결한 키를 서버에서만 사용한다. 고객 화면·요청에는 키와 모델 입력이 없다. 서버는 로그인 계정의 계산 요약으로 GPT-6.1 Terra / xhigh를 호출하고 키를 자산 DB·응답·로그에 남기지 않는다. D1에서 계정별/전체 일일 한도, 요청 간격, 동시 요청 잠금을 확인하며 한도 저장소 오류 시 호출을 차단한다. 실제 연결에는 별도 서버 비밀키 설정이 필요하다. 공개 전에는 신규 계정 남용 방지와 운영 비용 경보도 검토한다.

이 장치들은 공개 서비스에 대한 침투 테스트나 포괄적인 보안 감사를 대신하지 않는다. 특히 현재 호스팅의 인증 헤더 신뢰는 플랫폼 안에서만 유효하며, 일반 호스팅으로 옮길 때는 반드시 검증된 서버 세션으로 교체해야 한다.

## 권장 구성

| 영역 | 제안 |
|---|---|
| 로그인 | Google 또는 카카오 로그인 + 검증된 인증 서비스. 비밀번호를 직접 구현하지 않음. 카카오는 제공사 설정·심사 확인 필요 |
| 회원 식별 | 변경되지 않는 내부 회원 ID로 자산·거래·월별 기록 연결. 이메일은 로그인 수단으로 분리 |
| 데이터 접근 | 모든 서버 요청에서 세션 확인. 테이블의 user_id별 읽기·쓰기 제한. Supabase 선택 시 RLS와 서버 권한을 함께 적용 |
| 세션 | Secure·HttpOnly·SameSite 쿠키, 명확한 만료와 로그아웃·세션 철회. 관리자는 MFA 필수 |
| 저장 | 전송·저장 암호화, 최소 권한, 중요 키는 서버 비밀 저장소. 백업도 동일하게 접근 제한·삭제 주기 적용 |
| 운영자 접근 | 일반 운영 화면은 가입·활성·오류 등의 집계만 표시. 금융내역 열람은 별도의 제한된 권한·사유·감사 기록 필요 |
| 입력·API | 서버 검증, XSS/CSRF 방어, 계정별 요청·용량 한도, AI 비용 한도, 반복 로그인 제한, 종속성 점검 |
| 로그 | 비밀번호·세션·API 키·자산 금액·메모를 로그와 오류 분석에 기록하지 않음 |
| 탈퇴·복구 | 내보내기, 계정 삭제, 백업 보관 기한, 복구 절차와 복원 테스트 |
| 출시 전 | 다른 계정 ID 변조, 읽기·수정·삭제·백업의 계정 격리, 세션 만료, 권한 없는 관리자 접근, 데이터 삭제를 검증 |

예시 운영 구조는 공개 안내 사이트 + 로그인 금융 앱 + 인증 서비스 + 회원별 DB이다. Supabase Auth/Postgres는 후보이며, 현재 프로젝트에 새로 생성하거나 연결하지 않았다.

## 광고와 금융정보

광고 사업자의 JavaScript가 같은 페이지에서 실행되면 화면에 보이는 금융정보를 읽을 수 있다. 광고를 넣을 위치를 시각적으로 나누거나 금액을 가리는 것만으로는 격리가 되지 않는다.

1. 가장 먼저 공개 소개·도움말·금융 콘텐츠 페이지에 광고를 배치한다.
2. 광고 페이지와 로그인 금융 앱은 서로 다른 origin을 사용한다. 인증 쿠키는 앱 호스트에만 적용하고 금융 API에는 공개 사이트의 CORS 접근을 허용하지 않는다.
3. 계정 ID·이메일·대출·예금·주식 금액·메모를 광고 타기팅, URL, 분석 이벤트에 보내지 않는다.
4. 로그인 화면에서 광고가 꼭 필요하다면 외부 광고 코드를 금융 화면에 직접 넣는 대신, 별도 origin의 제한된 iframe 등 격리 방식을 검토한다. postMessage에는 금융정보를 전달하지 않는다. 광고사의 기능·정책과 격리 지원 여부도 확인한다.
5. 일반 배너와 데이터 기반 맞춤 광고를 구분한다. 광고·분석 쿠키와 선택적 마케팅 동의는 필수 서비스 동의와 분리한다.

## 회원가입과 업데이트 추적

회원가입은 사용자의 기록을 같은 회원 ID에 연결하고 여러 기기에서 이어 보게 한다. 월별 변화는 날짜·기준일·수정 시각을 가진 계정별 기록으로 보관한다. 서비스 운영 통계는 사용자 수, 활성도, 기능 이용 등 필요한 범위의 집계로 수집하고 금융 입력값을 분석 이벤트에 포함하지 않는다. 금융기관 잔고 자동 갱신은 별도의 기관 연동과 동의가 필요한 다른 기능이다.

출시 전 개인정보처리방침·이용약관에 수집 항목, 목적, 보관·파기, 위탁·국외 이전 해당 여부, 광고·분석·AI 전송, 이용자 권리를 실제 공급업체와 배치 지역에 맞춰 기재한다. 운영 사업자와 대상 이용 국가가 확정되면 적용 의무를 확인한다.

## 출시 순서

회원 인증과 계정 격리 → 백업·삭제·운영자 권한 → 오류·남용 감시와 비용 한도 → 제한된 사용자 테스트 → 공개 콘텐츠 광고 → 금융 앱 안 광고 필요성 재평가.
